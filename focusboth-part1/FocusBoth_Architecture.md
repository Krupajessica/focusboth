# FocusBoth — System Architecture and Implementation Plan

Jessica  |  Individual Applied Research Capstone, Fall 2026  |  Version 1.0

---

## 1. What the system does

FocusBoth is a web application for international students on F-1 OPT and STEM OPT. It answers one question that no existing tool answers in a single place: *is this job or this career path actually feasible before my work authorisation ends, and does this week still leave room for rest, hobbies, and family?*

The system combines four things: a visa clock built from the student's own dates, a live feed of real job openings pulled from public employer job boards, a deterministic rules engine that tests each option against hard immigration deadlines, and a weekly wellbeing budget that treats hobbies and rest as planned commitments rather than leftovers.

**The governing design rule of the whole architecture: the rules engine decides, the language model only explains.** Feasibility is never generated by a model. It is computed from dates and public data in plain TypeScript, so every answer can be reproduced and audited. A language model is used only to phrase what the engine already computed. FocusBoth is a guide and a monitor, not a lawyer and not a therapist.

## 3. Layer-by-layer detail

### 3.1 Presentation layer

A single responsive layout renders on desktop and mobile from one CSS design system with no component library dependency. The shell in `components/app-shell.tsx` provides persistent navigation across the six screens and displays the boundary statement — *guide and monitor, not a therapist, not a lawyer* — on every page.

### 3.2 Application layer

Six screens, each mapped to one user need:

- **Today** (`/`) — the daily briefing: days of work authorisation left, unemployment days used, application momentum, and the single strongest next action.
- **Visa Clock** (`/visa`) — the student's own dates: programme end, EAD start and end, unemployment days used. Everything downstream is computed from this screen.
- **Job Hunt** (`/jobs`) — live openings with filters, plus the personal application tracker.
- **Path Navigator** (`/paths`) — compares career scenarios against four hard rules and reports months of runway.
- **Wellbeing** (`/growth`) — weekly hour quotas for hobbies, learning, and rest, with progress tracking.
- **Discover** (`/discover`) — live hackathons and nearby tech and hobby events.

### 3.3 Domain layer — the rules engine

This is the intellectual core of the project and it contains no AI. `lib/compass-engine.ts` exports pure functions that take the student's profile and a job or path and return a decision plus the reason for it. Because the functions are pure, the same inputs always produce the same output, which is what makes the tool defensible for high-stakes decisions.

`lib/job-feed.ts` holds the parsing rules applied to raw postings: `parseSalary` extracts a published pay range from pay-transparency text, `classifyWorkType` separates internships from full-time roles by title, and `isUnitedStates` filters locations.

### 3.4 Server layer

Three route handlers run on the server, never in the browser. This matters for three reasons: API keys stay server-side, responses are cached so the external services are not hammered, and the browser makes one request instead of fifteen.

| Endpoint | Method | Behaviour | Cache |
| --- | --- | --- | --- |
| `/api/openings` | GET | Calls 15 Greenhouse boards in parallel with `Promise.all`, normalises every posting to one `Opening` type, sorts newest first | 30 minutes |
| `/api/salaries` | POST | Fetches full posting bodies for on-screen rows only, maximum 60 per call, regex-parses the published range | 24 hours |
| `/api/events` | GET | Devpost open and upcoming hackathons, plus Ticketmaster when a key is configured, deduplicated by URL | 30 minutes |

Each outbound call carries a timeout (15 seconds for openings, 12 for salaries) and a board that stops resolving is skipped rather than failing the whole response.

### 3.5 External data layer

Only sources that publish an open, documented endpoint are used. LinkedIn, Indeed, Google, and Instagram are deliberately excluded — their terms prohibit scraping and Instagram's event API is limited to professional accounts the app user administers. This is an explicit design decision, not a gap.

### 3.6 Persistence

Today the student's data lives in browser `localStorage` under three keys (`focusboth-data-v1`, `focusboth-growth-goals-v1`, `focusboth-saved-events-v1`), normalised on load so older saved records survive schema changes. Nothing personal leaves the device. Phase 2 replaces this with an authenticated Postgres database.

## 4. Runtime walkthrough — from search to application

Figure 2 traces the most important path through the system. Every step is code that runs today.

![Figure 2](FocusBoth_Data_Flow.png)

**Figure 2 — runtime data flow across the four tiers.**

1. The student opens `/jobs` and sets filters: United States only, posted within seven days, a role keyword, and a minimum pay figure.
2. `SuggestedOpeningsTable` mounts and issues a single `GET /api/openings`, showing a loading state.
3. The route handler fans out to 15 Greenhouse boards in parallel.
4. Each board returns its complete list of open postings from a public endpoint that requires no key.
5. The server normalises every posting into the shared `Opening` type, sorts newest first, and caches the result for 30 minutes.
6. The browser applies filters locally — location, posted window, employer, role, work type, and pay — then paginates from ten rows up to all rows in a scrollable table with a sticky header.
7. For the rows actually on screen, the client posts to `/api/salaries`, which fetches those posting bodies and extracts published pay ranges.
8. Postings without a published range are shown honestly as *not listed* rather than estimated.
9. The student clicks **Apply** on one row.
10. `applyDestination` returns the exact posting URL when one exists and the company openings page only as a fallback, then opens it in a new tab. FocusBoth never fills in or submits an application form.
11. The job is saved to the tracker and the rules engine immediately re-checks it: does the start date fall before the EAD end date, and how many unemployment days remain?
12. The Today dashboard reflects the consequence — days remaining, allowance used, and any conflict flagged.

## 5. The decision engine in exact terms

These are the rules the professor can inspect line by line in `lib/compass-engine.ts`.

**Unemployment allowance.** The cap is 150 days for STEM OPT and 90 days for standard OPT. Remaining days are the cap minus days already used, floored at zero.

**Job feasibility** (`jobPassesConstraints`) requires all three of: a sponsorship signal of at least 60, a résumé fit of at least 65, and a start date on or before the EAD end date.

**Path feasibility** (`evaluatePath`) applies four checks and a path is feasible only if all four pass:

1. The path starts on or before the EAD end date.
2. The commitment is at least 20 hours per week.
3. The employer participates in E-Verify.
4. A bona fide employer relationship exists.

When a path fails, the system names the failing rules rather than producing a score, and it reports runway in months so two feasible paths can be compared on substance. Every recommendation ends by directing the student to verify with their DSO.

| Student's own entries | Typed into the app | — | Live | The student owns and controls it |

## 7. Step-by-step implementation plan

### Phase 0 — foundation (complete)

1. Scaffold Next.js 16 with TypeScript and the App Router; build the custom responsive design system.
2. Define the shared type model in `lib/types.ts`: `VisaProfile`, `Job`, `Opening`, `PathScenario`, `SalaryRange`.
3. Implement the rules engine as pure functions with no external dependencies.
4. Implement client state and `localStorage` persistence with schema normalisation on load.
5. Build the six screens and wire them to the engine.
6. Build the three server route handlers and integrate the live public data sources.
7. Verify: lint, type-check, production build, and manual smoke test of every screen.

### Phase 1 — accounts and a real database (weeks 1–2)

8. Add authentication (Clerk, or Auth.js if a zero-cost path is required). Deliverable: sign-up, sign-in, and a session-scoped user ID.
9. Provision managed Postgres on the free tier (Supabase or Neon). Model tables for profile, jobs, paths, goals, and saved events, keyed by user ID.
10. Replace the `localStorage` calls behind the existing store interface with database reads and writes, so no screen has to change. Migrate any local demo data on first login.
11. Verify: two separate accounts cannot see each other's rows; row-level security is enabled.

### Phase 2 — the sponsorship signal (weeks 3–4)

12. Download the DOL OFLC LCA disclosure files and load them into Postgres offline. This is batch data, not a live API.
13. Aggregate filings by employer, role family, and year into a lookup table.
14. Replace the current placeholder sponsor score with the computed signal, and display the underlying filing count so the number is explainable rather than opaque.
15. Verify: hold out one quarter of filings and confirm the signal ranks known-sponsoring employers above non-sponsors. This is the quantitative evaluation of the project.

### Phase 3 — grounded AI with citations (weeks 5–6)

16. Assemble a corpus from public USCIS and SEVP guidance pages, chunked with source URLs attached.
17. Embed the chunks and store them with pgvector in the existing Postgres instance.
18. Implement retrieval-augmented generation with a hard constraint: the model may answer only from retrieved chunks, every answer carries citations, and if retrieval returns nothing relevant the system says so rather than guessing.
19. Keep the model strictly outside the decision path. It phrases the engine's output; it never computes feasibility.
20. Verify: build a question set with known correct sources and measure citation accuracy and refusal behaviour on out-of-scope questions.

### Phase 4 — deployment, testing, and presentation (weeks 7–8)

21. Deploy to Vercel (native fit for Next.js) or Cloud Run if a container is preferred, with secrets in the platform's environment store.
22. Add continuous integration on GitHub: lint, type-check, and build on every push.
23. Add automated tests — unit tests for every engine rule, integration tests for the three route handlers with mocked upstream responses.
24. Run a small usability evaluation with international students and record task-completion and trust findings.
25. Finalise the written report, the demo script, and the presentation.

## 9. Security, privacy, and boundaries

- Immigration dates are sensitive personal data. Today they never leave the device; after Phase 1 they are scoped to an authenticated user with row-level security.
- API keys live only in server environment variables and are never exposed to the client bundle.
- The application never submits a job application on the student's behalf. It redirects; the student decides and submits.
- Every visa-related screen carries a boundary statement directing the student to their DSO or a qualified attorney.
- The Wellbeing module budgets hours. It offers no counselling, no diagnosis, and no therapeutic advice, and it surfaces the 988 crisis line rather than attempting to help directly.

## 10. Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| A public job board changes or removes its endpoint | Boards are configured in one file and failures are skipped per board, so the feed degrades instead of breaking |
| The LLM states an immigration rule incorrectly | The model is architecturally excluded from decisions and may answer only from cited retrieved sources |
| Coverage is narrower than LinkedIn or Indeed | Stated openly as a scope decision: legally accessible sources with exact apply links, rather than scraped volume |
| Phase 2 runs long | Phases are ordered so that the system is demonstrable and complete at the end of every phase |
| Salary data is incomplete | Only published pay ranges are shown; missing ranges are labelled *not listed* and never estimated |
